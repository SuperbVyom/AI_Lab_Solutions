# Logical Reasoning for Planning: Submission

## Planning problem

Initial state: `{At(Robot,A), At(Package,A)}`. Goal: `{At(Package,C)}`.

| Action | Preconditions | Add effects | Delete effects |
|---|---|---|---|
| Move(A,B) | At(Robot,A) | At(Robot,B) | At(Robot,A) |
| Move(B,A) | At(Robot,B) | At(Robot,A) | At(Robot,B) |
| Move(B,C) | At(Robot,B) | At(Robot,C) | At(Robot,B) |
| Move(C,B) | At(Robot,C) | At(Robot,B) | At(Robot,C) |
| PickUp(Package,A) | At(Robot,A), At(Package,A) | Holding(Package) | At(Package,A) |
| Drop(Package,C) | At(Robot,C), Holding(Package) | At(Package,C) | Holding(Package) |

Initially `PickUp(Package,A)` is applicable because both facts in its precondition hold. `Drop(Package,C)` is not applicable: neither `At(Robot,C)` nor `Holding(Package)` holds.

## Hand plan and states

| Step | Action | Resulting facts |
|---:|---|---|
| 0 | - | At(Robot,A), At(Package,A) |
| 1 | PickUp(Package,A) | At(Robot,A), Holding(Package) |
| 2 | Move(A,B) | At(Robot,B), Holding(Package) |
| 3 | Move(B,C) | At(Robot,C), Holding(Package) |
| 4 | Drop(Package,C) | At(Robot,C), At(Package,C) |

This plan achieves the goal. The BFS planner in `logical_planner.py` uses states as immutable sets of propositions. An action applies only when positive preconditions are present and negative preconditions absent; effects delete then add facts. The goal test checks that all goal facts are included in the current state.

## Tests and results

| Test | Result | Validity |
|---|---|---|
| Original problem | `PickUp(A), Move(A,B), Move(B,C), Drop(C)` | Each action's preconditions hold; final state contains `At(Package,C)` |
| Remove pickup action | No plan found | Correct: no action can establish `Holding(Package)` |
| Irrelevant robot movement | A move can change robot location but cannot satisfy `At(Package,C)` | Goal predicate is checked on package, not robot |

Logic determines whether an action is applicable and computes its successor state. Search chooses which applicable action sequence to explore. The decision sequence is: current state -> test preconditions -> discard inapplicable actions -> apply effects for applicable actions -> enqueue unseen successors -> test each state's goal condition.

For plan verification, independently executed state transitions are stronger evidence than an LLM's prose explanation: the transition checker evaluates the formal preconditions and effects step by step. An explanation can omit a failed precondition or claim a fact that was never added.

## LLM prompt and reflection

**Prompt:** “Write a small STRIPS-style planner for this three-location warehouse. Represent facts as a set; each action has positive/negative preconditions and add/delete effects. Apply only applicable actions, use BFS over immutable states, prevent revisiting states, detect no plan, and print the action plan and each resulting state. Use exactly the action schema and initial/goal facts supplied; do not infer additional actions.”

Preconditions and effects should be specified first so code cannot silently permit impossible moves or package operations. If preconditions are skipped, the robot might drop a package it is not holding. A plan that sounds reasonable may contain such an illegal step; every step must be executable from its preceding state. The LLM contributes implementation structure and boilerplate; independent verification checks the transitions and goal. Logic appears in action applicability/effects, while planning is search over the resulting state graph, closely related to BFS from the search lab.

### Optional Prolog verifier

```prolog
connected(a,b).
connected(b,a).
connected(b,c).
connected(c,b).
can_move(X,Y) :- connected(X,Y).
valid_move(X,Y) :- connected(X,Y).

wet_road.
slippery :- wet_road.
reduce_speed :- slippery.
```

`can_move(a,b)` succeeds because `connected(a,b)` is a fact; `can_move(a,c)` is not established because no matching edge fact exists. The rule encodes `Connected(X,Y) -> CanMove(X,Y)`. `reduce_speed` succeeds by the chain `wet_road` fact -> `slippery` rule -> `reduce_speed` rule. Prolog facts are ground assertions; rules derive conclusions for matching facts. Queries ask whether a goal follows under the program's inference procedure. An independent Prolog check can catch unsupported moves in a plan generated by a separate Python system.
